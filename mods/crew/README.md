# crew

**Work in progress.** crew is a resident product-development team inside Claude Code. Your main conversation coordinates it.

```
/plugin install crew --marketplace PeterTing/claude-mod
```

Five roles take a PRD to tested code, and you approve the designs:

1. **PM** splits a PRD into features and acceptance criteria.
2. **QA** writes a test case for every criterion.
3. **UI/UX** writes a design for every feature: a screen, with its layout, states, interactions and copy, or no screen, with why. You approve each one, or send it back with a reason (gate **G2**).
4. **Tech lead** breaks the criteria into tasks: what to build, for which criteria, and how big (S, M, L, XL). Gate **G3**, checked by code, needs a task for every criterion. The tech lead also reviews each task's code (gate **G5**).
5. **Full-stack** builds the tasks. Each commit's message starts with its task's id (`TASK-003: …`), and crew reads the commits to see what is built. How hard the task is (易, 中, 難, 極難) picks the model, from the role's floor up (see [Claude or Codex](#run-a-role-on-claude-or-codex)).

  Several builders at once (同時做任務 in the 設定 tab: 1 to 8 agents, 4 by default, the tech lead's review counted):
  - Tasks that change different files build side by side, each with a builder of its own (全端, 全端 2 … 全端 8) on a branch and worktree of its own, made from crew's branch. A task whose files overlap another's under way, or that changes a shared file (a package manifest, a lockfile, a migration, a schema, a router, a config), waits, as does one that comes `after` another; one whose plan names no files runs alone. While more than one agent may work, crew asks the tech lead once to name the files of the tasks that name none (a board planned before builds ran side by side, say), so they can build side by side too. The tech lead plans shared ground (types, schema, API contracts) first.
  - The tech lead reviews one task at a time. While more than two tasks wait for review, no new build starts.
  - An approved task is merged back into crew's branch by crew, one at a time, and the tests (those crew finds in the project and yours) run on the result before crew's branch moves. A merge that conflicts, or that fails a test case that passed before, is taken back, and the task goes back to its builder with what to do. A test case that passed in the last run (no command failed it) and that any command which ran both times fails now is taken as broken by the merge, whichever command passed it before; a command that ended 0 before, now ends otherwise and tells no test case apart counts too. A command you changed or added since, or one for a folder the merge adds, says nothing of what the merge broke: its results count as any run's, and do not take the merge back. When the files that say the packages (`package.json`, a lock file, `requirements.txt`, `pyproject.toml`, `go.mod` and the like) differ from those your worktree prep command last set crew's worktree up for (a merge taken back since counts), or that run failed, the prep runs again there before the tests. If it fails, the merge stops without running the tests; that is this computer's to set up, not the task's, so no builder is told and nothing counts against the task. crew asks you one question for all the merges stopped so (one stopped later is added to it, never asked apart), with the tasks, the end of the output and its log: set the computer or the command right (the 設定 tab's ［試跑］ on the worktree prep row tries it in crew's worktree), then answer it with anything. crew then runs the prep once more in its worktree and, if it succeeds, the stopped merges in the order they stopped; if not, it writes the new reason into the same question and waits for your next answer. It never tries again by itself; ［接續］ tries them again too. While the flow is held (after a restart, until ［接續］), only your own answer, in the pane or on crew's page, runs them again: one Claude passes on is held then, as any answer is. `/crew reset` forgets the stopped merges with the flow. Meanwhile the board shows those tasks as 合回停住：準備指令沒跑成功, the 記錄 tab shows the run as 合回前準備 and each merge as 沒有合回, and the other tasks go on. Once the merge goes in, what the prep rewrote of the files git tracks (a lock file) is put back; what it left untracked, such as the packages, stays. A found command whose runner is not installed there even then cannot run: that is this computer's, not the task's, so it never takes the merge back, and what it passed in the run before is kept to compare the next merge with (never shown as a result of this one). After three merges taken back for the tests, you decide, and your answer goes to the builder with the last run; the question says what to do when the output is of packages missing on this computer. Say it needs no change, and once its builder commits nothing crew merges it as it is: the test cases and commands that run found broken (those its question named, not what failed before it too) no longer take this task's merge back, while every merge is still compared with crew's branch's own latest run, and those test cases still count as failed at the test gate until they pass. A merged task's branch and worktree are removed.
  - Past the usage warn line, one agent works at a time. With 1, once no task is left on a branch of its own, the full-stack builds one task at a time in crew's own worktree, as before. Then, once the tech lead approves a task's commit, crew runs your test command on that commit in QA's worktree (the builder goes on in crew's own), one approval after another, and a test case that passed in the last such run and fails now sends the task back to its builder. Past three such times, you decide: what you answer goes to the builder with that run's result, and if you say to leave it and the builder commits nothing, crew records the commit approved again and compares later approvals' runs with that run. A run that passes counts afresh. While an earlier task sent back so owes its fix, later tasks are not tested this way; the run once every task is done tests them all. The builder may run your tests in crew's worktree at the same time: tests that need a fixed port or a shared local database can then fail for that alone.
  - Each task gets a builder with a fresh context. Two settings help it start ready:
    - **worktree 準備指令** (設定 tab). Your own command, such as `bash scripts/crew-worktree.sh`. crew runs it in every worktree it makes: its own branch's, each task's, and one made again after it was removed. It runs again in crew's own worktree when a merge needs it (see above) and when you try it, with `CREW_AGAIN=1`: write it so that a second run does no harm, such as a `ln -s` that first checks the link is not there yet. It runs before a builder starts there, with no shell, for at most ten minutes. The script gets `CREW_MAIN` (your checkout), `CREW_BASE` (crew's own worktree), `CREW_WORKTREE` (the new one) and `CREW_TASK`, so it can link the packages or copy the ignored env files. crew never reads those files.
      - A builder given work there waits, shown as 準備 TASK-003 的 worktree, and is told how the run went.
      - On a failure it still starts, told the last 20 lines.
      - The output is kept in `.crew/runs/setup-*.log`.
      - ［試跑］ runs the command once in crew's own worktree. While crew merges a task there it is refused: try again once the merge is over.
    - **固定附上給每個全端** (記憶 tab). Memories every fresh builder is given, whatever its task, ahead of the related ones: up to 12, about 1,000 tokens. A builder or the tech lead pins one when it saves it (`builders: true`), and the memory that replaces a pinned one stays pinned. You pin one by its id, or take a pin off.

  What counts as built:
  - Only commits on crew's branch count, made after crew made the branch and on no other branch. A `TASK-001: …` in your own history is not crew's work.
  - crew remembers each commit it has seen, and the task it did, so a merge or a deleted branch does not undo it. A later task that takes the same id on a board made again is not counted built by the earlier task's commits.
  - A commit that an amend, a rebase or a reset takes off crew's branch no longer counts: the task is built by what the branch still holds. So after a squash merge, delete crew's branch rather than resetting it to your main branch: a reset takes crew's commits off it, and its tasks would be built again.
  - A task whose worktree still holds changes not committed is not counted built: the full-stack is asked to commit them, revert them, or add build output to `.gitignore`.
  - A commit makes a task under way. It is done once the tech lead approves its newest commit.

Then the code is checked twice:

- **Review.** Once a task is committed, the tech lead reviews it with the diff crew attaches, and sends its verdict with `review_submit`: approve, or the changes to make. crew pins the verdict to the commit the tech lead read, and keeps it on this machine. A newer commit makes the review out of date, and the task is reviewed again. Changes go back to the full-stack, and its next commit is reviewed; after three rounds of changes, you decide.
- **Test runs.** Once every task is approved, crew runs the project's tests in its worktree, one command after another, each for at most ten minutes: the commands crew finds in the project, and yours (set in the pane's 設定 tab), at most five in all.
  - **crew finds the commands itself.** Before every run, every merge's tests and every run on a tech lead's approval, crew looks again at the newest commit there, with `git ls-files`, `git grep` and `git show` alone (never in `node_modules`, `vendor` or `.git`; at most 40 manifests, nearest the root first, in folders that hold tests). It knows three kinds: a `package.json` with a `test` script runs as `npm --prefix <dir> test` (`pnpm --dir <dir> test` or `yarn --cwd <dir> test` when the nearest lock file is pnpm's or yarn's); a `go.mod` as `go -C <dir> test -v ./...`; pytest settings (`pytest.ini`, `[tool.pytest.ini_options]` in `pyproject.toml`, `[tool:pytest]` in `setup.cfg`) as `python3 -m pytest -v <dir>`, or `uv run python -m pytest -v …` with a `uv.lock`, `poetry run python -m pytest -v …` with a `poetry.lock`. Python tests with no pytest settings are listed, not run. crew builds each command from these fixed forms alone, never from a command the repo writes (a README, a Makefile, CI files), and runs it with no shell; a folder whose path cannot go in a command safely is listed, not run. A repo with no tests at first therefore needs nothing from you once tests are added: the next run, merge or approval finds them, and the 設定 tab marks them 新找到.
  - **Order and the five places.** Your commands take places first (they run after crew's, in your order), then folders whose tests name test case ids, then the rest by path. Those past five are listed and not run, and their test cases are G6 gaps; turning one off lets the next one in. A command of yours crew can read as running a whole folder (such as `npm --prefix backend test`, `go -C svc test ./...` or `pytest tests/`) runs in place of crew's for that folder; any other runs beside crew's, which may run some tests twice rather than miss any. Only flags that change the output or what is measured alone keep a command whole: npm's, pnpm's or yarn's own before `--` (`--silent`, `-s`, `--quiet`, `--verbose`, `--loglevel <level>`, `--color`), and after `--` the runner's long ones (`--reporter=…`, `--reporter <name>`, `--verbose`, `--silent`, `--colors`, `--coverage`, `--ci`, `--runInBand`, `--watchAll=false`, `--watch=false`, `--passWithNoTests`, `--maxWorkers=…`); for go `-v`, `-count=1`, `-race`, `-timeout`, `-cover`, `-covermode`, `-coverprofile`, `-coverpkg`; for pytest `-v`, `-q`, `-s`, `-rA`, `--tb=…`, `-p no:cacheprovider`, `--cov…`, `--no-cov`. A short flag after `--` (`-v`, `-s`, `-t`…) means what the runner makes of it, and any other flag (`--testNamePattern`, `--shard`, `--onlyChanged`, `-short`, `-failfast`, `-x`, `--co`…) may run part of the folder, so crew's command for it still runs. Once the root's `package.json` test script runs, crew leaves the subfolders' `package.json` to it, unless the root's output named none of a subfolder's test files: that subfolder's own command runs too from the next run.
  - **What you see and decide.** The 設定 tab lists each folder crew found: its place, command, the file and setting it came from, its folder, its last result and why it does or does not run, with 不要跑這條 or 恢復 (`/crew test-found off|on <key>`). Only your own press or typed command turns one off or back on; that choice is kept on this machine, and a turned-off folder's test cases are G6 gaps (你關掉了). The brain, the roles and the board cannot turn a folder off or on, change your commands, or add or remove what crew found. A key with spaces or other odd characters in it cannot always be typed; press the row's button in the 設定 tab instead. A found command that cannot start, or whose runner is not installed, marks that row 跑不起來: it does not decide the run's result, its test cases have no result and stay G6 gaps, and the others still run and count. A runner is taken as not installed only when the command ends not 0 with no test case failed and no totals, and what it printed says so. crew reads stdout and stderr apart, past what npm, pnpm, yarn, corepack, uv and node print of their own (npm's `npm warn` lines, yarn's `info` and `error Command failed`, pnpm's `ELIFECYCLE`, `ERR_PNPM_…`, `Done in` and `Already up to date`, the script's `> name test` banner, node's stack header): one of the two begins with the line that says so, and the other has nothing of its own. Whole lines alone count: the shell's `sh: vitest: command not found` with exit 127 (or the exit code pnpm or yarn end with), cmd's `'vitest' is not recognized as an internal or external command,` on Windows, node's `Cannot find module '…/node_modules/jest/…'` or `Cannot find module 'mocha'`, node's ESM loader missing a file of the runner's own package that the package imports (installed in part), `…/python3: No module named pytest` with the program's path spaces and all (`python.exe` too), or uv or poetry failing to start it. A runner that started prints its own lines first, so a config that imports what is not there, or a test module's own import, stays the run's. crew does not look for the runner before it runs the command (Yarn Plug'n'Play has no `node_modules`, and a runner may be installed elsewhere): what the command prints is the evidence. When the command ran to its end in the same worktree before, why says on which commit, and which package files changed since or that none did (this computer's packages went); a worktree crew made again keeps none of that. The run's summary, its toast and its log name each found command that could not run, with its exit code (or that it could not start) and why; when none could, the run has no exit code of its own. A command of yours that cannot start stops the run, as before. When you turned off every command crew found and set none of your own, G6 says so (crew 找到的測試指令都被你關掉了).
  - **Nothing found.** When crew finds nothing to run and you set nothing, the tests do not run: crew tells you once, the first time the tests' turn comes, then says it only in the 設定 tab and G6. The flow goes on without asking you, and the test cases with no result stay G6 gaps (沒跑到), never passes.

  Each command's output is kept in a log file of its own, with an index listing them; the run's summary is a line per command; a test case another command failed stays failed, whatever another says. Each test case passes or fails by the lines of the output that name it, such as `✓ TC-003 …`, `test_TC_003 … ok` or `--- FAIL: TestTC003`, so tests carry the id of the test case they check (gate **G6**). A result is pinned to the commit it ran on, and the output is kept as evidence in `.crew/runs/`. crew runs the tests only on a clean worktree at the newest commit, so a result is that commit's: keep build and test output (`__pycache__/`, `coverage/`…) in `.gitignore`, or crew asks you first. A test the runner skips (TAP's `# SKIP`) has no result. Failures go to the full-stack on the task they serve; its fix is reviewed and the tests run again. After three runs, or when the command cannot run, you decide. A test case the output has no result for (often a backend test or a manual check your commands do not run) is not a failure: running the same commit again gives the same, so crew neither runs again nor wakes the full-stack for it. crew finds why from the test files on its branch (`git grep` for the id in files named like tests — `*.test.*`, `*.spec.*`, `*.e2e-spec.*`, `*_test.go`, `test_*.py`, `*_test.py`, `*_spec.rb`, `*Test.java`, or anything under `test/`, `tests/` or `__tests__/` — `git ls-files` for the folders test runners work in, and their `package.json` and `go.mod`): 沒跑到 (a test file names it, in a folder no command runs: a command crew can read, such as `npm --prefix frontend test`, `go -C svc test ./...` or `pytest tests/`, does not reach it, and the output names none of that folder's test files; crew names the folder and why the command it found there did not run: you turned it off, it is past the five places, its Python tests have no pytest settings, it could not start, or its path cannot go in a command; a folder crew found no runner settings for is named alone, for you to set a command in the 設定 tab. Those you turned off, and those of a run that had nothing to run, are not asked about: they stay G6 gaps with their reason), 看不出有沒有跑到 (a command crew cannot read, such as a script, `npm run test:ci` or `npx vitest run`, a command that runs part of a folder, or a test file no runner folder holds, such as RSpec or Java, and the output names none of its files: crew does not say it was not run, and the full-stack can still be asked to look), 被跳過 (the output says the test was skipped; with several commands, crew lists what each one skipped, with a line it printed), 有跑到但輸出沒有列出結果 (the file ran, or another test file in its folder shows the folder's runner ran, unless a command told that runner to run fewer, such as a name filter, a path or a shard, but no result line names the id: often a runner that lists only failed tests, such as vitest without `--reporter=verbose`), or 找不到測試 (no test file on crew's branch names it). It asks you once, with the run's overall result (such as `exit 0；Tests 4870 passed (4870)`), the failed and the no-result test cases listed apart with how many, the no-result ones grouped by why: go on without them (跑不到不算失敗), or have the full-stack take them on, each as its reason asks (add tests named with their ids, name the tests that ran with their ids, find why they were skipped, or check that a command reaches them and lists their results); a typed answer that does not ask for the tests is taken as going on without them, and crew says back how it took it. After a run that did not end cleanly, asking the full-stack sends it to find why the command did not end as it should, even when every one of them went to QA for another way: those go with that fix as its reason, with no tests to add, until a run ends cleanly or every test case is verified another way (a run with no gap left goes on, as any does). Test cases you answered on are not asked again on later runs, merges, PRD changes or a restart on the same PRD while they still have no result; you are asked only about what changed: a new one with no result, or one that had a result and lost it. One whose reason changed after you answered (沒跑到 becoming 被跳過, say) is not asked again: the pane's G6 shows its reason now, with your answer. A question still open whose test cases' reasons change on a later run is asked anew. A question too long to read whole cuts its lists, never how to answer. When every one of them is 沒跑到 and the run ended cleanly, crew offers only going on: tests from the full-stack would not reach a folder no command runs, a command for it would; a typed request for the tests is then not taken, and crew says so. They stay G6 gaps, not passes: the pane's G6 says you answered on them, and crew's closing line counts them apart. A run that ended with an exit code not 0 while no test case failed, and that gave no test case a result or printed no totals crew reads, may have stopped before it reached them: the test cases it gave no result for go to the full-stack, 沒跑到 ones too (a command that stopped short names few files), for it to make the command run to its end; once it does, those no command reaches are asked about as 沒跑到. One that went to its end (its totals printed) asks you the same question, saying the command ended with that exit code, and also offers having the full-stack find why the command did not end cleanly; a failed test case explains an exit code not 0 by itself. With several commands, a run counts as having gone to its end when at least one printed totals and every command that ended with an exit code not 0 printed them.
- **Test cases no automated test fits.** A test case is verified by your test commands unless you set it another way, on its page (the 看板 tab, or a G6 gap) or on crew's card in 待你決定: **QA 實際操作** for a check that needs eyes on the screen (QA operates it in the app crew starts and reports it passed with a screenshot of its own, in `check_report`'s `shot`), or **你驗收時確認** for a delivery check only a person can judge (it is listed on the feature's 待你驗收 card with its steps and what it should show, and passes only when you tick it as you pass the feature). QA proposes another way with a reason (`propose_check` on the board); a test case with no test file naming it gets 請 QA 提議其他驗證方式 in the no-result question too. Proposals wait on one card of crew's: 照這樣設 takes them all, 照這個設 or 不要 on a row takes one, and 都不要 takes none (a proposal said no to is not asked again; another is). Only your own press sets a way: QA, the brain and anything on the board cannot. The way is set for the test case as it stands, so a case QA rewrites goes back to the test commands, and you can set it back to 測試指令 on its page any time. Evidence counts only for the way set: QA's on a commit holding every one of the feature's tasks' latest commits, out of date once those tasks have a newer one (QA operates it again on the feature's next check), and your tick as you pass it. A failure is never relaxed: a test command failing the case fails it whatever its way, QA's failure goes to the full-stack as any check's, and 要改 on the card goes the usual way. G6 counts each way's passes apart (each test command's, QA's, yours) and waits for QA's, not for yours: those wait for your acceptance, which the feature needs anyway. With no app set, QA's wait reads 「等 QA 實際操作：這個 repo 還沒設定 app」 and crew asks how to start the app as it does for pictures. crew keeps the ways you set and their evidence in its own store, not on the board, and marks the board from it.
- **Asked before the build.** When you have set no test command of your own and QA's app is not set, crew asks once, before the first task is built, for what QA starts the app with; it names whatever is not set. It does not ask for a test command: crew finds the project's itself (see Test runs). Answer to go on, set or not: what is not set is skipped, and said so.
- **QA in the running app.** Once every task of a feature is merged, crew starts your app with your start command and QA checks the feature in a real browser before you see it, one feature at a time. The app runs in QA's own worktree, `.crew/work/<name>-qa`, at the newest commit of crew's branch, so QA sees the features as merged and nothing a builder is still writing; your worktree prep command runs there the first time. crew waits up to two minutes for your app's URL to answer. QA walks the feature's test cases at desktop (1440) and phone (390) widths, takes screenshots, reads the console, and for a feature with no screen calls its API itself. It reports what it saw with `check_report`, a result for every test case crew listed (however many: crew reads a report up to 1000 test cases, and never fewer than it listed) and something to look at for each criterion (up to three), screenshots at both widths for a screen; crew sends back a report short of that, and one with a result other than passed, failed or blocked (crew never takes one for another), a blocked test case with no note saying why, or one test case reported with two different results. Only the test cases crew listed for the round count: another feature's, or one you confirm yourself, passed or not operated, neither passes nor waits there; a failed one not on the list sends the report back, for QA to correct the id or leave another feature's out, and so does a failure in failed under a criterion that is not this feature's: a report holds this feature's failures only. A failure on criteria none of the feature's tasks covers goes to no task: crew asks you, rather than putting it on the feature's first task, with two options. 請 Tech lead 補一項開發工作來修 has the tech lead add a task for those criteria; once it is built, reviewed and merged, QA checks the feature again (should the tech lead add none, crew asks you again). 我覺得 QA 看錯了，請 QA 再檢查一次 has QA operate it again on the same commits, told what it reported and to report what it sees; when a task covers those criteria by then (the tech lead added one), the check waits for that task's new commit instead, as the same commits would show the same. Neither passes the feature, and the flow is not done while the failure stands. When QA could operate none of the test cases, none is set to QA in the app and the feature has no screen you approved, nothing to look at is asked for; a feature with an approved screen always comes with its screenshots. Then crew stops the app: it runs your stop command (設定's 關掉 app 的指令) there when one is set, and ends only what it found listening on the URL's port once the app answered and that started after its start command; a program running before, such as Docker's own, is left alone. A failure waits for a free builder, ahead of tasks not started, and goes to the full-stack on the task of the criterion that failed, in QA's words; its fix is reviewed and merged, and QA checks again. After three rounds you decide, and your answer goes with the fix; say it needs no change, and once its builder commits nothing the feature is taken as it is. A test case QA could not operate (no test account, or nothing to see in the app, such as lint or git) is kept apart from failures, and never counts as passed: its evidence stays what it was. With nothing failed, those verified by your test commands keep nothing from you: the feature is handed over, their G6 still from your test commands. The check reads 通過 only when QA passed in the app every test case it was given; with some passed and others it could not operate, or set to you to confirm on crew's question, it reads 部分通過 with how many of each; with none passed, whatever it showed you, it says QA confirmed no test case in the app, and why, and its pictures are not waited for again. The pane and crew's closing line count these apart from passes, each test case once. Those you set to QA in the app are asked about, once a round, saying what is missing and where to set it (the 設定 tab's test accounts file): 已經處理好，請 QA 再試一次 has QA try again, and 這些改成我驗收時自己確認 sets them to be confirmed by you on the acceptance card, as choosing 驗收時確認 on its test case does, and hands the feature over, as passed only for what QA passed; only your own press or typed answer sets that, not one the brain passes on, and only for that feature's test cases as crew listed them for its check, with your own words kept in the decision crew records. A typed answer counts only as an explicit pick: an option's words as they read, with crew's label and the words after it or without; crew's labels alone (A／1, B／2, A/1, B/2, their letter and number agreeing); or its place (1 or 2, ２, A or B, 第一個 or 第二個, 前者 or 後者, 2 號, 2 號選項, #2, No.2, option 2), alone or with a yes or thanks around it (選 2 好了, 好，2, 2，謝謝, OK 2; that 好了 is the pick's, not a word that anything is handled). For the first, also an answer that is nothing but asking QA to try again, in phrasings crew lists (請 QA 再試一次, 麻煩再試, 重新試試看, 再跑一次, retry, try again), after words saying it is handled (帳號設好了，請 QA 再試一次) or before 「如果還是不行再跟我說」 at most: crew reads no other words as trying again. Words to stop or that say a try is no use (停, 取消, 放棄, 算了, 夠了, 一樣, 浪費, 沒用, stop, cancel, enough, pointless), or a question, keep any answer from picking, and words that only say it is handled (帳號設好了, 可以了) pick nothing. Anything else is not guessed at, whatever it seems to mean, and an answer ending in a question mark never picks: crew asks again, records no decision and posts nothing to the roles, and QA does not run and nothing changes meanwhile; after two such answers in a row it asks you to press an option or reply 1 or 2. Such an answer the brain passes on is not taken, and the question stays open for you. ## Let the brain take a repo over

You do not need a PRD to start. Press 讓大腦接手這個 repo on the pane's start screen (or 接手這個 repo in its 設定 tab, or type `/crew lead on`), and in that repo your main conversation leads the team from your first message:

Those questions sit at the top of the draft on 待你決定頁, the whole PRD folded below them, and the draft starts only once they are answered and the brain has changed the draft to match. Under a question, ［問大腦］ asks the brain about it instead of answering; the brain replies in that comment thread. Once you say yes in the conversation, or press 確認，開始 in the pane, the flow starts and the roles report back to the brain.
- Small things, such as a bug fix or a change of copy, the brain does itself, with no PRD.
- A batch of bugs, a fix across modules, or work you already wrote a spec for is feature-sized too: it goes through crew, and with an empty board the brain drafts the PRD from your spec.
- The roles' work (splitting, designing, test cases, planning, review, building) goes to the roles: the brain does not start agents of its own for it.
- When you turn takeover on, the brain lists the work it already has going (its own agents, open PRs) and asks you, for each, whether it goes on or goes to crew.
- A decision or preference the brain records for you carries your own words. One without them is the brain's judgment, and the roles read it as 「大腦的判斷，使用者沒有明說」, entries from before 0.7.0 included. A question you ask back is not a decision.

In a repo not taken over, Claude still knows what crew is for: told to use crew, it does, and it does not do the roles' work with agents of its own.

The switch is yours alone: the brain, the roles, another plugin and a repo's own files cannot turn it on. It is kept on this machine, per repo, not in git, so other repos are not affected. Turned on in a conversation already under way, the brain hears it there: at once, or with the next role's report while a role is at work. A new session has it from its first message. Turned off, the brain goes back to working as usual and its draft is dropped (the file stays). crew never commits the draft.

A program you start yourself in that worktree during a run and put in the background is ended too (or within about 20 seconds after a reload or restart cut the run), and so is a background service your worktree prep started there while a Codex run was under way (a 試跑 you start then). When the commit fails, the builder hears why when it can fix it (conflicts left, a nested repo, a big folder `.gitignore` should hold); otherwise you are asked at once, with git's words and what each answer does, and only that task waits. A full-stack on Claude commits itself, as before. When Codex is logged out or out of quota, a role on 系統預設 goes to Claude (or asks you first, as 大腦換模型前 says); one you picked waits for Codex.

A Codex run is a process of crew's own: a reload of crew (an edit to a mod loaded with `--plugin-dir`, or a restart) ends it. The role stops with 「Codex 這一輪被 crew 重新載入打斷」, which is not Codex's fault. When the reload took a new version of crew in the same Claude Code, crew starts the flow's run again by itself, once the flow stops (no other role at work, nothing waiting for you), and says so: 「crew 換上新版了（HH:MM）。PM 剛才在 Codex 上的那一輪重新開始。」 While it waits, it says what for, and a reload meanwhile keeps that word, taking along the flow's runs it cuts too. A run you asked a role for, a reload of the same files with no such word waiting, and a load after crew was switched off for more than two minutes start nothing at once: they are left as any run cut short, for 接續, or for crew's heartbeat to wake the flow once within five minutes (see Failed runs). A flow you held stays held. After a restart of Claude Code the flow waits for 接續, so nothing is spent before you say so. Roles on Claude go on.

Claude Code takes a new version of crew's files only where it watches crew's folder (`CLAUDE_CODE_PLUGIN_DIR_WATCH=1` for a folder in `CLAUDE_CODE_PLUGIN_DIRS`). crew looks at its own files every half minute: when the files on disk have differed from the ones it runs for a minute, the short pane beside crew's web page says 「crew 有新版本還沒換上・換的方法在網頁上」, and crew's web page says how to take the new version, with a button that copies `/reload-plugins`. A page beside a crew too old to say its version shows the same.

## crew looks after its work

- **A heartbeat every 5 minutes**, in code, with no model call:
  - A running flow with nobody at work and nothing waiting for you: crew wakes the role its stage waits on, once. If it stops at the same place again, the pane asks whether to try again.
  - A finished flow takes on only what came after the finish: a newer commit goes to the tech lead's review, a test result out of date to a new run. Work an older board never had (designs, test runs, unbuilt tasks) waits for you.
  - A question you left for two hours is brought up once.
  - The pane's 常駐 line says when crew last looked, what it found and did, and where a restart went on from. The look when Claude Code starts only marks the time.
  - A role the heartbeat, the PRD check, a test run or the end of a Codex run needs to start afresh starts at Claude Code's next action (a command, a prompt, a tool call, a role's turn end, any press in the pane), not from the timer itself: the engine runs an agent a timer starts as crew's own code and skips crew's hooks for it, so it could use none of crew's tools. In a quiet session, once a role has waited 30 seconds, crew sends Claude a fixed one-line note (「叫醒排著的角色」), at most once every 2 minutes; Claude's short reply gives the frame. Each note costs that one short turn, and the 記錄 tab lists it as 「叫醒大腦」. Waking a role whose agent is still there works from the timer.
- **No question dialog while crew works.** While a role works, waits to start, or the flow is in a stage roles work in (and not paused), Claude's own question dialog (AskUserQuestion) is refused. Another plugin's dialog is not. Claude is told to ask with crew's `ask_person` on 待你決定頁, or in plain words in its reply. A dialog left open keeps Claude Code waiting for you, so crew could wake no role: in one repo two such dialogs held the work 20 and 22 hours. With crew at rest, Claude asks as usual.
- **The Mac stays awake while crew works.** crew runs macOS's own `caffeinate -i -s` for two minutes at a time, and again while a role still works or waits to start, QA checks a feature, or crew runs your test command or a worktree prep. Once they all stop, the Mac sleeps as usual within two minutes. The pane says 「Mac 保持清醒中」 meanwhile. A closed lid still sleeps the Mac, and nothing works while Claude Code is closed. On a machine without caffeinate, crew does nothing here.
- **Claude's usage limits.** Your subscription has a 5-hour and a 7-day limit, and crew's roles share them with your own conversation. crew reads the same numbers as `/usage` (never your login) and shows them under the PRD line and in the Token tab:
  - At 80% of either window it tells you once, and tells Claude when Claude leads.
  - At 90% of the 5-hour window, or 95% of the 7-day one, it pauses the roles on Claude. A role at work finishes the run it is on. Work for the others waits in their inbox, and the pane and the line above the prompt say 「crew 暫停中」. Roles on Codex go on. When Claude leads, crew tells it not to hand out feature work meanwhile.
  - At the window's reset crew goes on by itself, in the order the work came. ［這次照常做］ lifts the pause until that reset.
  - A run cut short where a window is used up waits for the reset the same way, with no ［接續］ needed. This holds even with the guard off.
  - The Token tab turns the guard on or off and steps the thresholds (warn 70–85%, pause 85–95% for 5 hours and 90–98% for 7 days).
  - With an API key there are no such limits and no numbers, and the guard does nothing.
  - crew never switches accounts or suggests one to get past a limit.
- **Token reminders**, worked out in code, each condition at most once an hour and again only once its numbers are worse: a role over 40% of the day; a role reading under 60% from the cache (both only on a day, and a role, over 50K tokens); a role past its context threshold; two senders going back and forth on one item more than six times, while they still are; a role's single tool output over 10K tokens. Claude hears of each, and the Token tab lists them with the time.
- **What Claude may do about usage.** With the `crew` tool's `tune`, Claude can set a role's engine, model, effort or rotation threshold for its work from now on, never below the floor you set for that role. A move of engine, model or effort follows 大腦換模型前 in the 模型 tab. A threshold follows 大腦處置 in the Token tab: by default Claude asks you first, and its proposal waits under 待你決定. With 自動, Claude may raise a threshold up to 256K, as an at-least one (a harder piece of work keeps its own, higher one), giving the reason and telling you it did; lowering one, or going past 256K, still waits for you. Either way each action is kept as a decision, one you approved as yours, and the Token tab shows the role's numbers before and since. Nothing skips a gate, a test or a review to save tokens.
- **A threshold is not the context's size.** Past it, nothing stops: the role starts afresh the next time it is woken. Within one long turn Claude Code compacts the role itself, and crew tells Claude when it did. Claude rotates a role only with a reason, which the log keeps as 「大腦輪替：…」. A role at rest, or one marked to start afresh, gets no hourly reminder about its threshold.

## The board stays on the PRD, live

- **Every requirement is numbered.** crew reads the PRD itself. These are requirements:
  - in a section with a list: each list item, with its wrapped lines, and each table data row;
  - in a section without one: each paragraph, except one ending with a colon (a lead-in);
  - the text under the title, only when the rest of the PRD holds no requirement.

  These are not: front matter, code, comments, quotes, headings, breaks, lines that are only an image or a link, context sections (背景, 參考, 附錄, 概述, Background, References…), and the dated or versioned entries of a revision history (修訂紀錄, Change log). So write requirements as list items; a paragraph in a section with a list is not tracked.

  Each requirement gets a number from its words, such as `R-3fa2c1`. The number stays while other lines change or the spacing changes, and changes when its own words do. That number is crew's own, for the roles to link features to requirements. The pane shows the PRD's own number instead, a different one for each requirement:
  - the id the item starts with: `FR-03 —`, `[REQ-12]`, `**US-4**`, a table row's id cell (the first cell, bold or in code marks too, or another cell that is an id like `FR-7` no other requirement has, so a `對應需求` column citing `FR-1` gives no row `FR-1`). A dotted number an item starts with (`- 2.1 登入`) is its number where it goes on from the heading over it, or, with no heading number over it, where another item beside it starts with one too; not a share or a size (`1.5 倍`, `2.5 GB`). A dotted first cell such as `3.1` is the row's number when its column's header says so (`編號`, `ID`, `#`), and never when the header names something else (`版本`, `日期`); with neither, it is the row's number when it goes on from the heading over it (`3.1` under `3.`) or when no heading over it has a number, so a version table's `1.1` under `5.` is not. Where a column's dotted cells are its rows' numbers, its whole ones are too (`1`, `1.1`, `1.2`, `2`). An id with no separator (`R1：`) counts only as one of a series in its section (`R1`, `R2`), and only where no other requirement starts with it; a priority (`P0：`) or a version (`v2`) is never an id;
  - else its numbered list's numbers, where they are all different;
  - else its place, counted under the nearest heading with a number (`2.3`), passing over the numbers the PRD gives others there, or through the whole PRD where no heading over it has one. A heading's number may be `2.`, `2.1`, `3、` or `二、`, and its bold or link marks do not hide it. A number with nothing after it to say so (`2 人氣排行`) is a heading's when a heading beside it, at its level under the same one, goes on from it (`1 帳號`, `3 結帳`), whatever words follow it. Alone, it is not one where it is a count after a whole number (`3個角色`, `10 分鐘內`; a count is told by its whole word, so `7 個人資料` and `5 元件` are headings) or a share after a dotted one (`1.5 倍`). Not a heading's number either: a year (`2024 年`), and the document title's (`# 2.0 訂閱改版`). An item nested in another takes the parent's number first (`2.3.1`).

  Where two requirements would still share a number, the one most like the PRD's own numbering keeps it (its own id, then one under a numbered heading); where none is more like it, each takes its section's name after it. A requirement reworded or taken out of the PRD, which the board still holds until the PM links again, goes by crew's number and says it is no longer in the PRD, with the number it had, so no two show the same number. The pane groups the requirements under the PRD's headings, the outer headings first (`功能 A › 需求`); those before the first heading are under `PRD 開頭`. A requirement's page names both numbers and says where its number comes from. The roles are given both too, so a question about `需求 2.3` reaches the right one. The board keeps the numbers with its baseline, so the pane still shows them while the PRD cannot be read. Anything crew takes for a requirement that is not one can be moved out of scope by the PM, with a reason. crew tracks up to 1,000 requirements per PRD.
- **The PM must cover every requirement.** The PM's features name the requirements they answer. Gate **G0**, checked by code against the PRD file as it stands, needs:
  - every requirement answered by a feature, or moved out of scope with a reason;
  - every feature answering a requirement that is still in the PRD.

  The split is not done until G0 passes.
- **A changed PRD is caught within seconds.** crew checks the PRD file every 10 seconds; the check itself calls no model. When it changes:
  - the pane and the line above the prompt show what changed;
  - the PM is told which requirements were added and removed, once per change;
  - the flow goes back to the split, and cannot finish until the board answers the PRD again; then QA writes tests for what is new only.

  It also runs when Claude Code starts, so an edit made while it was closed is caught too. An added requirement is told at once. A removed one is confirmed on the next check, about 10 seconds later, so a file caught half-saved is not taken for a real edit. A PRD with no requirements left is never sent to the PM.
- **A PRD is a document in the repo.** crew starts `.md`, `.markdown`, `.mdx`, `.txt`, `.rst`, `.adoc` and `.org` files, outside private places such as `.git`, `.crew`, `.ssh` and `.env*`, wherever a link leads. Its requirements go on the board, which is in git.
- **A PRD crew cannot read is called out.** The pane and the line above the prompt say so when the PRD is deleted, moved, swapped for a link, or holds no requirement. crew then keeps holding the board to the requirements it last read. Each new version of the PRD is checked before and after crew reads it: it must still be a file in the repo, reached through no link.
- **A board synced to another PRD is called out too.** A teammate's board, or another branch's, may be synced to another PRD. crew then says so and holds nothing to it until you choose, in the pane's 設定 tab: the board's PRD to follow it, or yours to move the board over.
- **Starting a PRD the board already mostly answers checks it, without a new split.** The board is held to the PRD as it stands: the PM fills what is missing, and QA tests what has no test case. A PRD the board answers less than half of is split, and the PM is told which requirements already have features.
- **A PRD change while QA is writing tests keeps that QA.** The PM syncs; when QA's run ends, QA is asked for the new criteria only.
- **The pane says how current it is.** It shows how the board stands against the PRD, when the PRD last changed, and when crew last looked.
- **Progress is counted per requirement.** The Progress tab lists each PRD requirement with how far each stage of its development is, all from the board, git and crew's own records:
  - spec: every feature that answers the requirement has criteria;
  - design: those features have a design you approved;
  - test cases: those criteria have test cases, counted done only once the spec is;
  - tasks: those criteria have the tech lead's tasks, counted done only once the spec is;
  - code: those tasks have a commit on crew's branch; done once the tech lead approved each task's newest commit;
  - review: those tasks approved at their newest commit; `⟳` when an approval is out of date;
  - test results: those criteria's test cases passed in crew's latest run, on the newest commit; `⟳` once a commit came after the run.

  Each row shows the requirement's first sentence, and its number opens the full text with everything under it. A note under the table says how each column counts. A requirement moved out of scope shows the reason instead. The overall row above the table uses the same seven stages, in the same order. Overall progress counts a design as done once approved, code once reviewed, and a test case once passed, so it reaches 100% only when all of that is true; every percentage is rounded down. A task the tech lead planned shows in the recent work as `排定：<title>`: the plan is what was finished, not the task.
- **One board, several PRDs.** Starting another PRD keeps the earlier one's requirement numbers on the board, so its features stay its own and do not hold up the new PRD's split. A board from before crew numbered requirements is not reported as a PRD change: the PM is asked to link its features to the requirements.

The other roles' searches in your checkout see it too. |
| `.crew/work/<name>-t003/` | no | A task's own worktree while builders work side by side, on branch `crew/<name>-task-003`. Removed once the task is merged back. |

Where the board is kept, the flow, the open questions, who started the work, your test command, and, for each PRD, crew's branch, the commits it has seen, the tech lead's reviews, crew's latest test run and your decisions on designs are not in the repo. crew keeps them in its own store on this machine, keyed by the repo's path. A repo you clone therefore cannot start work by itself, and the marks a board carries (commits, reviews, test results, approved designs) count for nothing until crew has recorded them itself. On another machine, crew starts without that record: the board shows no code built there until crew sees the commits on its own branch. Where crew keeps the board is kept too, so it never moves under the work on another branch: `.crew/` once crew wrote its board there, the root once crew took a board up there, until that board is moved into `.crew/`.

crew adds `usage/`, `log/`, `work/`, `runs/`, `codex/` and the page files under `designs/` to `.crew/.gitignore` and leaves your own rules there alone.

crew's root in a session is the folder Claude Code started in, and it stays there when crew is reloaded or the shell moves into a subfolder or a worktree. A subfolder that is a git repo of its own is that repo's. A session started in a linked worktree of the repo, as Claude Code's desktop app does (`.claude/worktrees/…`), is the same project: crew works from the main repo there, with its settings, PRD, board and progress. Run crew in one Claude Code at a time per project: when two sessions (the terminal and the desktop app, say) have crew open on one project, the pane, a toast and `.crew/session.json` tell them apart, and crew says so once every half hour while it goes on. Only one copy of crew writes the board at a time. Each copy (the marketplace's, a `--plugin-dir` one) keeps its own record of commits, reviews and decisions, and the board's marks follow that record, so two copies writing one board would keep taking each other's marks off. The first copy to write the board says so in `.crew/writer.json`, and says it again while it follows its PRD. While that word is less than a minute old, any other copy changes nothing on the board and says why, once; it keeps its own record meanwhile, and puts its marks on once it writes again. Close every conversation on the project that runs the copy you do not want: a minute later, the one you keep writes again. Every Claude Code that runs one copy writes as that copy: another conversation, a restart, a reload, a `/clear` or an older version of the same copy is the same writer. A copy from before `.crew/writer.json` neither says nor heeds that word; leaving a board aligned to another PRD alone is what keeps it from taking marks off. crew also leaves alone the marks on a board aligned to another PRD (the commits, reviews and design decisions of that PRD's tasks), keeps a decision you make then in memory only, and refuses a `board_write` there until you choose which PRD to follow.

## Safety

- **Secrets are masked.** Anything that looks like a key, token, password, private key, JWT, connection-string password or bearer token is masked before it is written anywhere crew writes. Words in a rule, like 「密碼：至少 8 個字元」, are left alone. A design's mockup is not masked, since masking would break its code: one that looks like it holds a secret, even a variable such as `token=++seq`, is sent back to the designer to rewrite, and nothing of it is written. Masking works by pattern, so a secret in an unusual shape can still get through: keep secrets out of PRDs and answers.
- **crew never writes over what it cannot read, nor outside the repo.** A board it cannot parse (a merge conflict, a typo) is left as it is until you fix it. So is a board with a part crew cannot read, such as a feature whose `test_cases` is not a list: the pane says which part, the line above the prompt and `/crew status` show 「⚠ 看板讀不到」, and the work stops there. A feature with no criteria or test case list yet is read as having none, and crew adds the empty list when it next writes the board. A `prd-tracker.json` at the repo's root is the repo's own, read by its own tools, unless crew made it there before 0.5.2: crew reads it only to tell whose it is, never writes it, and keeps its board in `.crew/`. A file in the board's place that is not crew's board, one with no `prd_items` list, is neither read nor written either, and crew cannot start until it is fixed or moved. A file of crew's that is itself a link, or whose path leads out of the repo, is neither read nor written. That includes a file that links to another file inside the repo. A directory link on the way is followed only when it lands inside the repo. Either way crew tells you why.
- **Write tools take only crew's own callers.** Only crew's roles and the main conversation can write to the board, threads, questions or memory. Other agents and the roles a reset retired cannot.
- **Each role has its own permissions on the board.** The PM edits features and criteria; QA writes test cases; the designer writes designs; the tech lead plans tasks and sends reviews. The full-stack cannot write the board at all.
- **Some decisions are yours alone.** Approving or sending back a design, setting how a test case is verified (and ticking the ones you confirm as you pass a feature), setting the test command, the worktree prep command, the start command, the app's URL or the test accounts file, pinning a memory yourself, approving Claude's proposals on usage, and saving your preferences take your own press or field in the pane, a `/crew` command you type at the prompt yourself, one you send from your Remote Control client, or your comment on 待你決定頁, which the brain passes on word for word. Claude's `crew` tool cannot do them, and neither can another plugin, another Claude session, a channel relay, a schedule, an answer to a question, or anything written on the board.
- **Claude's actions on usage keep to your floors.** A model or effort below the floor you set for a role is refused, whether Claude asks you first or acts on its own; and nothing skips a gate, a test or a review to save tokens.
- **QA's check runs your app and a browser.** crew starts your app by your start command's words, with no shell, in QA's worktree, with your environment, `CREW_QA=1` and `BROWSER=none`. It does not start it when something already answers at the URL or listens on its port, which may be your own app, and says so. Once QA is done it ends the app and what listens on that port then, which nothing did before. What the app prints is masked into `.crew/runs/`. QA's browser is `@playwright/mcp` 0.0.84, which `npx` fetches the first time, headless and with a fresh profile each run. crew refuses any page QA asks it to open that is not on this machine (`localhost`, a name under it, `127.0.0.1`), and the browser's own filter (`--allowed-origins`) blocks requests to anywhere else, the app's own fonts, scripts and APIs from elsewhere among them (QA reports what breaks for that alone as blocked, not failed); that filter is not a wall, and a redirect the app makes is not checked. It takes a dev server's own certificate. It writes only screenshots, by a name crew checks, into `.crew/qa-shots/`. QA cannot edit files or run commands. Of your files it reads only the test accounts file you set, and is told to type what it holds into the app's login alone. Its report is refused whole when a field looks like it holds a secret (a password, token, key, cookie or one-time code, or a user and password pair such as `user / pass`; a word of letters alone counts as a password only assigned to a password key, `password: …`, `密碼是 …`, `password is …`, or to a secret, token or passphrase key with `:` or `=`, and not a word of the screen such as `optional` or `verified`) or holds a value from the test accounts file you set, which crew compares in memory only, in any case, full width, %-encoded, base64 (an `Authorization: Basic` header too), spelt with spaces or with invisible characters (zero-width, a soft hyphen) in it; a password of the file always counts, except one of letters alone that is a word of screens and code (admin, password, test, demo, secret, user, guest, root, pass, changeme, qwerty, letmein and a few more) or the same as an account name of the file: crew cannot tell such a password from the word, so it counts only where it reads as a login (after a password or account key, `admin / admin`, `用 admin 登入`), and the 設定 tab suggests a test password with a digit; an account name that is also an ordinary word (`finance`) counts only beside a login word or its password, a number only as a number of its own (`/orders/48210` is not `4821`); the refusal names the fields, never the value, and nothing of a refused report is kept or asked about. While crew cannot read that file whole (gone, unreadable, a link, or over 16 MB) QA is not started and no report is taken: crew asks you once to set the file right or clear it, checks no other feature till you answer, and on your answer looks at the file again, starting QA only once it reads it. QA's last words, and those of the QA that looks for how to start the app, are never passed on when they hold any of this: crew says it left them out. What crew keeps of a report it takes is masked too. A command, URL or file a repo or a board names is never used: crew keeps yours on this machine, and Claude cannot set them.
- **crew's web page stays on this computer and your own devices.** Its server listens on `127.0.0.1` and, while Tailscale runs here, on this Mac's Tailscale address for devices logged in to your own Tailscale account; never on every address, never through Funnel. This computer's browser gets in with the one-time key in crew's link; a request naming another host is refused. See [Decide on crew's web page](#decide-on-crews-web-page).
- **Keeping the Mac awake changes no setting.** crew runs only `/usr/bin/caffeinate -i -s -t 120`, with no shell, while roles work or crew runs your tests or a worktree prep. Each run ends by itself, so none outlives the work.
- **Your test commands run without asking each time.** crew runs each in its worktree on crew's branch, by its words, with no shell (no pipes or `&&`), for at most ten minutes each, with your environment and `CI=true` (so a runner does not wait in watch mode). crew runs them as you set them and prepares nothing a test needs: a test that needs a database is run by a script of your project's that prepares it. They run code the full-stack wrote, outside your Claude Code permission prompts, with whatever keys your environment holds, so set them only for a repo whose code you are willing to run. A command a repo or a board carries is never run as written: crew keeps yours on this machine, and builds the ones it finds from fixed forms (see Test runs). A test runner still runs what the project configures (`npm test` runs the `test` script in `package.json`), so taking a repo over with crew runs its tests: turn a folder off in the 設定 tab if you do not want that. A run that breaks down on the way (a full disk, a reload) says so instead of leaving the flow waiting, and opening Claude Code on a flow that stopped while testing runs the command again once you press 接續. A new version of crew loaded in the same Claude Code runs it again by itself.
- **Your worktree prep command runs the same way.** It runs by its words, with no shell, for at most ten minutes, with your environment, `CI=true` and the `CREW_` paths. It runs in a worktree crew just made, before any builder works there, and again in crew's own worktree for a merge that needs it or a trial (`CREW_AGAIN=1`), so it must be safe to run twice. A task's worktree is made from crew's branch, which the builders commit to: a script named by a relative path is that worktree's copy, which a builder may have changed. Keep the script outside the repo and name it by its absolute path, and only what you wrote runs. What it leaves untracked there, such as a link to `node_modules`, is not taken for a builder's uncommitted work. crew keeps it on this machine, and Claude cannot set it. Copying env files is your script's work: their values never pass through crew or a role. A builder told of a failed run is asked not to read or print them.
- **Test output stays out of git.** The evidence in `.crew/runs/` is masked and ignored by git. The end of a failing run's output goes to the full-stack alone, never into the repo's threads, since it may hold values masking does not recognize.
- **The full-stack works in crew's worktree, not your checkout.**
  - It starts in `.crew/work/<name>`, a git worktree on branch `crew/<name>` that crew makes from your checkout's commit; with several builders, each task has a worktree and branch of its own made from crew's branch. It is told to leave your checkout and branches alone and not to push. crew merges the tasks into crew's branch; merging crew's branch into yours is yours.
  - That is an instruction, not a fence. The full-stack edits files and runs commands under your Claude Code permission mode, like any agent, and crew says so once when the build starts.
  - After each of its runs, crew checks your checkout: new changes, another branch or another commit, and your other branches. It also notices a change to its own files (the board and the memory) that crew itself did not make; one made a link, moved out of the repo or unreadable counts as changed and is not read. If anything moved, crew says what, since it cannot tell whether you or the full-stack did it.
  - A commit on crew's branch that changes the board or `.crew/` is pointed out to the tech lead, who is told to have it undone, and to you.
  - A `crew/<name>` branch crew did not make is not used: crew makes one with a new name beside it. Nor is one that holds neither the commit crew last saw on it nor, in its own reflog, a move from it, such as a branch deleted and then checked out again from a remote: crew reads none of its commits and says so. An amend, a rebase or a reset of crew's branch keeps it crew's.
  - crew itself runs only `git rev-parse`, `git symbolic-ref`, `git status`, `git worktree add`, `git log` (with `-g` for the branch's reflog), `git merge-base`, `git for-each-ref`, `git show` and `git diff --name-only` (the diff for a review), `git grep` and `git ls-files` (to find the project's test commands and tell why a test case has no result), with the repo's hooks and file monitor off, and your test commands. With several builders it also merges a task back: `git checkout --detach`, `git merge --no-ff` (or `--abort`), your test command, then `git update-ref` to move crew's branch only from where it left it and `git checkout` back onto it, or, when the merge conflicts or breaks a test, `git checkout --force` and `git reset --hard` back to crew's branch as it was; it then removes the task's worktree with `git worktree remove` (which refuses one with changes) and its branch with `git branch -d` (which refuses one not merged), and brings a task's branch up to crew's with `git merge --ff-only`. For QA's check it makes QA's worktree with `git worktree add --detach` and moves it to crew's newest commit with `git checkout --detach --force`, and runs `curl` and `lsof` to see whether the app answers, `kill` to end it, and `mkdir`, `rm` and `cp` for QA's screenshots. These run only in crew's worktrees, on crew's branches. A folder that is not a git repo, or one with no commit yet, stops the full-stack, and crew says why.
- **Your words stay yours.** Roles cannot save or replace your preferences, nor a decision you made or the main conversation relayed for you. The daily tidy-up saves only facts and lessons, never decisions or preferences.
- **Answers are marked by who relayed them.** An answer Claude relays for you is saved as `brain Q-nn`, so it stays traceable.

## How memory works

- **Saved as it happens.** Roles save decisions, constraints and lessons with `memory_save`. Two kinds of decisions are saved automatically:
  - your answers
  - the PM's scope drops

  Decisions share the board's `DEC-` numbering.
- **Found by id and by words.** A message that mentions `AC-003` finds memories that reference `AC-003` or its feature. Other memories are ranked by BM25 over Chinese character pairs and English words. Your preferences always come along. Superseded memories are never returned.
- **Attached, not loaded.** Starting a role attaches up to about 800 tokens of related memories. A fresh builder is also given the memories pinned for every builder, in a section of their own; a builder woken later gets the pinned ones it has not seen yet. So does waking one, but only with memories it has not seen yet. A wake also names the other items whose threads hold messages for the role.
- **Rotation.** A woken agent resends its whole conversation, so crew starts a fresh one instead when:
  - the role is past half its context limit
  - it moves to another model
  - you press 輪替 on its row in the pane

  This happens only when the role is idle: a role at work gets new messages in its inbox instead. The fresh agent gets the working set, the related memories, its recent thread lines and its last report.
- **Failed runs.** A run that ends in an error, an interrupt or a refusal does not move the flow on. crew's heartbeat wakes the role once within five minutes; press 接續 in the pane to go on sooner.
- **Compaction backstop.** If the engine compacts a role during one long run, the summary is told to keep ids, decisions and what is left of the task.

## Known limits

- **Telling a runner that is not installed from a test that fails.** crew reads a found command's output to tell a runner missing on this computer (which never takes a merge back) from the run's own failure. Some shapes are read the wrong way:
  - A `pretest` script that prints something first (`"pretest": "echo built"`), a `test` script that runs another command before the runner (`node -e "" && vitest run`), or a `package.json` with no `name` and `version` and a `pretest` of its own: the missing runner is read as the run's own failure, so the merge can be taken back for it. Installing the runner, by your worktree prep command, ends it.
  - A runner that starts, prints a `warning:` line of its own and then cannot find its own module: read as the runner missing, so that command does not take the merge back. Its test cases get no result from that run, which is a gap at the test gate, never a pass.
- **A comparison with a kept result may blame a later task.** When a found command cannot run on a merge, crew keeps what it passed in the run before and compares the next merge with that. A merge in between that broke one of those test cases while the command could not run is not caught then; the next merge that runs it is taken back for it, though another task broke it. Before you hold the task to it, check whether a merge since that command last ran broke it.
