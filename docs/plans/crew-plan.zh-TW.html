要有記憶，也要 RAG 化

要有記憶。context 只是工作桌，不是檔案櫃。重要的事一發生就寫進 repo（看板或記憶），所以任何角色的 context 隨時可以清掉重開，不會失憶。

也要 RAG 化。角色每次被叫醒時，mod 只把和這件事有關的幾條記憶（800 token 以內）附在訊息後面，不載入整段歷史。這樣 context 不會一直變大，角色也知道目前的狀況。

第一版用「編號連結＋關鍵字檢索」，不用向量。Claude Code 沒有提供 embedding 給 mod，要用向量就得另外跑一個 embedding 模型。專案記憶大多是編號、名詞和決策，用編號和關鍵字就找得到，而且不花 token。等抽考分數不達標，再加向量檢索。

目標與成功條件

我把「像 grok bot」理解成：一直在線、隨時叫得到、會自己定時看狀況、記得之前的事。如果你指的是其他特性，告訴我，我再調整。

整體架構

每個角色是 mod 開出的具名 agent，做完就閒置、收到訊息才醒來（第 0 階段實測確認，不需要實驗中的 agent team 功能）。角色之間不直接互傳訊息，而是寫進 crew 的討論串，由 mod 轉送並附上相關記憶。crew mod 也負責角色定義、模型路由、看板與記憶工具、token 計量和面板。所有狀態都存在 repo。

「常駐」怎麼做到

主 session 是團隊辦公室

在一個 Warp 分頁（或 tmux）開著 Claude Code 不關。角色在裡面閒置等訊息，閒置時不送請求，不花 token。

心跳只用程式檢查

mod 每 5 分鐘檢查新 commit、測試結果、卡住的項目、等你決定的問題。檢查不呼叫模型，有事才叫醒對應的角色。

重開就接續

Claude Code 重開時，mod 從 repo 讀回看板和記憶。角色有工作時才帶著乾淨的 context 和相關記憶上線，不重播舊對話。

遠端（選用）

可以搭配 Claude Code 的 Remote Control，從手機跟大腦說話。

做不到的是：電腦關機或 Claude Code 關閉時，團隊不會繼續工作。如果之後需要 24 小時運作，再評估用雲端排程處理固定工作，例如每晚跑一次測試。

Context 控制與記憶

用四道機制控制 context：事情一發生就存、喚醒時檢索、超過門檻就輪替、引擎壓縮時換成記憶包。輪替指的是：角色還是同一個人、同一個名字，只是把桌面清乾淨，換一份精簡的資料重新開始。

怎麼找出相關記憶

  • 編號連結：訊息提到 AC-07，就找出所有引用 AC-07 的記憶，以及 AC-07 所屬功能的決定。
  • 關鍵字：中文切成兩字一組，英文照詞切，用 BM25 排序。全部在 mod 裡用 TypeScript 計算，不跑外部程式、不連網。
  • 新近程度和角色：較新的、適用這個角色的排前面；被取代的排除。
  • 主動補拉：角色覺得不夠時，可以自己呼叫 memory_search。

輪替

mod 從每次請求的用量算出每個角色目前的 context。超過門檻時，等那個角色閒置下來才輪替，不打斷它手上的工作。

保底：如果角色在輪替前就碰到引擎的自動壓縮，mod 的 session.compact hook 會改用同一份記憶包取代，不再另外呼叫模型寫摘要，也比較省（S6 實測）。

大腦自己的 context：角色的例行回報不直接送給大腦，mod 每 30 分鐘合併成一則摘要；需要大腦判斷時才立刻送。大腦壓縮時也換成記憶包，並且可以用 memory_search。

模型與 effort 依任務動態分配

複雜度判斷依據（程式計算，不花 token）模型・effortcontext 門檻
S列清單、改文案、補單一 test case、格式整理Sonnet・medium60K
M一般功能、單一頁面或 API、驗收條件 3 條以內Sonnet・high100K
L跨前後端、驗收條件多、要改 schema 或多個模組Opus・high160K
XL架構決策、金流、權限、資料遷移、並行；或同一項目失敗兩次Opus・xhigh256K
  • 分級從哪來：PM 或 Tech lead 建立項目時標複雜度，程式再依關鍵字（migration、payment、auth、concurrency…）、驗收條件數量、牽涉的檔案數往上調。
  • 升級：同一項目測試失敗兩次或 code review 被退回，自動升一級。降級：連續幾個同類項目一次通過，下一個同類項目降一級。
  • 什麼時候換：中途換模型會讓 prompt cache 失效，所以只在角色接新項目或輪替時換模型；同一項目進行中只調 effort（是否影響快取列為 S8 實測）。
  • 大腦覆寫：大腦可以用工具指定某個角色或項目的模型，寫成一條決定；token 提醒也會列出各級別的用量，讓大腦調整分級規則。
  • 角色下限：Tech lead 不低於 Opus・high（架構和 code review 的漏判代價最高）；全端、PM 不低於 Sonnet・high；UI/UX、QA 不低於 Sonnet・medium。XL 失敗後再升一級用 Opus・max，並通知大腦。
  • 門檻與喚醒：門檻是「連續做同一項目時」的上限。角色閒置後要換做別的項目，或 context 已經很大，就帶記憶包重開，不叫醒長對話（實測：叫醒的成本約 1.25 倍 context）。

溝通規則

  1. 每則訊息都要掛項目編號（例如 AC-07、TASK-12），自動歸到那個項目的討論串。
  2. 訊息 400 字以內。更長的全文存到 .crew/notes/，收件人只收到第一段和檔案路徑。
  3. 角色之間不廣播，只有大腦能發全員通知。
  4. 例行狀態更新不送給大腦，由 mod 合併成摘要。
  5. 兩個角色在同一項目上來回超過 6 次、狀態都沒變，就交給大腦處理。
  6. 你可以用 /crew ask qa … 直接找某個角色，或在面板「待你決定」裡回覆。

介面設計稿

介面有兩部分：輸入框上方一行摘要，以及 /crew 打開的面板（五個分頁）。以下全部是示意資料。第 1 階段會把這些畫面做成 /crew demo，讓你在終端機裡實際點看、確認。

Token：只顯示，大腦自己優化

照你的決定，不設任何上限，只把用量攤開來看。用量異常時，mod 會用程式判斷並提醒大腦，由大腦決定怎麼調整。

顯示什麼

每個角色的輸入、輸出、快取讀、快取寫、快取命中率、目前 context、喚醒次數、輪替次數；大腦的協調佔比；每次喚醒附上多少記憶。

什麼時候提醒大腦

某角色佔今日總量超過 40%；快取命中率低於 60%；喚醒時 context 已超過門檻；兩個角色在同一項目上來回超過 6 次；單次工具輸出超過 10K token。同一個條件一小時最多提醒一次。

大腦怎麼調

依序考慮：輪替該角色、降低 effort 或換模型、精簡工具清單、把 task 拆小、調整訊息規則或門檻。每次處置都寫成一條決定，面板會顯示處置前後的對照。

底線：不能為了省 token 跳過關卡、測試或 code review。

第 0 階段實測結果（2026-10-15）

在 Claude Code 2.1.300 用 headless session 實際跑了 4 輪（主對話與測試角色都用 Haiku），每個事件都記錄成 log。下表的數字都來自那些 log。

項目結果對設計的影響
S1 角色定義與常駐通過 plugin 定義的角色照自己的模型和 effort 執行（Haiku・low，主對話是 medium）。具名 agent 做完會閒置，收到訊息就帶著原本的對話醒來。它是具名的背景 agent，不是 agent team 的 teammate。crew 不需要依賴實驗中的 agent team 功能，比較穩定。
S2 角色呼叫 mod 的工具通過 每次呼叫都帶 agentId，看得出是哪個角色。看板與記憶工具照原設計。
S3 量 context通過 每次請求都拿得到該角色的輸入、快取讀、快取寫。輪替判斷和 token 面板照原設計。
S4 輪替通過（換做法） 用同名重開就會產生新的 agent，舊的自動退役、名字轉給新的。閒置的 agent 不算執行中，TaskStop 會回錯誤，也不需要。輪替＝同名重開＋記憶包。
S5 訊息附上記憶原路不通，備案通過 mod 送給角色的訊息不會經過 session.receive。但訊息本來就是 mod 送的，記憶直接組進訊息內容即可。角色之間不直接用 SendMessage，一律透過 crew 的討論串工具，由 mod 轉送並附上相關記憶。
S6 壓縮換成記憶包部分 autoCompactWindow 可設定，但最小值是 100K。替換壓縮內容的 hook 要等 context 真的到 100K 才觸發，這次沒測到。全端的 100K 交給引擎；60K 的角色用 S4 的輪替。壓縮 hook 留到第 3 階段實測。
S7 角色固定成本已量測 只有 crew 工具：1.5K；加上讀寫檔與 Bash：4.2K；全部預設工具＋CLAUDE.md：9.7K–13.6K。工作角色的固定成本約 6–7K（含角色卡），60K 門檻下約有 53K 可用。
S8 動態換模型和 effort通過 每次請求都能改 effort，沒有額外的快取損失。改模型也會生效，但快取歸零（那次請求的快取讀是 0）。確認原設計：只在接新項目或輪替時換模型，進行中只調 effort。
新發現：喚醒的快取成本要處理 叫醒閒置的 agent 時，只有 system prompt（約 0.9K）讀得到快取，其餘對話整份重新寫入快取。也就是每次喚醒的成本約等於 1.25 倍的 context。新增「喚醒或重開」策略：context 大、又閒置的角色，改用記憶包重開（便宜）而不是叫醒。角色記得的事情靠記憶系統，不靠長對話。
新發現：大腦被通知叫醒已解決 每個 agent 做完一輪都會通知主對話。沒攔的那輪大腦被叫醒 5 次，每次重讀約 24K；在 prompt.submit 攔下後，被叫醒的次數是 0。例行完成通知一律攔下，由 mod 整理成摘要，有需要判斷的事才送給大腦。

測試工具的限制：headless 模式下，主對話閒置、背景 agent 也剛好都結束時，執行就會直接結束，所以多步驟的自動化測試要讓主對話保持忙碌。互動模式下 session 一直開著，不受影響。

第 2 階段：PM＋QA 實際跑通（2026-10-15）

在真的 Claude Code session 裡，用一份「待辦清單 App」小 PRD 跑完整流程；repo 裡放了你 ai-company 專案的嚴格 prd-tracker schema。

項目結果
拆 PRD通過 PM（M 級 Sonnet・high）拆出功能和驗收條件，PRD 沒寫清楚的地方用 ask_person 問，沒有自己猜。
寫 test case通過 QA 為每條驗收條件寫 test case，編號用 schema 規定的 SMK- 前綴；無法測的地方在討論串問 PM。
回答問題後接續通過 /crew answer 的答案轉給 PM，PM 依答案新增 7 條驗收條件，流程自動交給 QA 補 test case。
最後結果4 個功能、20 條驗收條件、48 個 test case，進度 100%；prd-tracker.json 用 ajv 驗證符合嚴格 schema。
大腦不被叫醒通過 最後一輪主對話沒有任何模型請求（用量裡沒有大腦的紀錄）。
tokenPM 約 229K、QA 約 213K，大部分是便宜的快取讀；輸出合計約 16K。

實跑才抓到的問題（都已修正）

  • Agent 工具的 model 只收別名（sonnet、opus），傳完整 ID 會被拒絕，角色根本沒啟動。
  • 開了 agent team 的 session 裡，角色會變成 teammate，完成時透過 team 信箱叫醒大腦。改成在信箱這關攔下角色的回報。
  • 用 agent.offer 把角色藏起來，也擋掉了 crew 自己叫醒角色；改成只在 crew 叫醒角色的那一刻開放。叫不醒時，帶著訊息開新的角色。
  • 流程完成後，QA 在討論串留給 PM 的問題沒人回；PM 依答案新增條件後 QA 也不會被叫回來。兩者都改成自動接續，來回最多 3 輪。
  • 「今天完成」原本把每次寫入都算進去；改成只算推進進度的事。
  • 重開的角色不知道問題已經問過，重複發問；board_read 現在會列出等你回答的問題。

已確認的決定（2026-10-15，第二輪更新）

  1. 名稱：crew。
  2. 模型：不寫死，依任務複雜度動態決定；effort 可用到 xhigh，升級時可到 max；Tech lead 下限 Opus・high。
  3. context 門檻：依複雜度動態決定，S 60K、M 100K、L 160K、XL 256K（三個模型的 context 視窗都是 1M）。
  4. 介面：總覽最上方顯示整體進度（完成數／總數、階段、目前在哪、今天完成多少），另有「進度」分頁看各功能與每天完成數。
  5. 關卡 G1–G6 可以點開：檢查什麼、誰補誰確認、覆蓋率、每個缺口的狀態，缺口有討論串的可以直接跳過去。
  6. 面板位置：全螢幕模式且終端機寬度至少 110 欄時，停靠在對話右側（和其他 mod 的面板共用分頁）；其他情況顯示在輸入框上方。
  7. git：流水帳和用量檔不進 git，其他都進。
  8. 開發順序：spike → 設計稿 → PM＋QA → 記憶 → 其他角色。
